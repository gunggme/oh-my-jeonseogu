## 1. 본인이 AI의 과잉 응답을 직접 지적했다

9월 23일 20:53, 참여자가 공유한 이미지에는 입력 `어이 전서구.`와 AI의 응답 `왜부름 / 무슨일임`이 보였다. 이후 전서구가 다음과 같이 말했다.

> 아닌데 / 전서구면 / ? / [다른 사람의 웃음] / 하나보내는데

다른 참여자는 비슷하다고 웃었지만, 본인은 이 장면에서는 물음표 하나를 보낸다고 구체적으로 지적했다. 재미있다는 반응과 실제 화자와 닮았다는 평가는 분리해야 한다.

이 사례의 문제는 단순한 글자 수가 아니다. 두 AI 문장은 사실상 같은 역할을 반복한다. 부름에 반응하면 충분한 순간에 용건을 요구하고 캐릭터 표현까지 덧붙인다. `?`에는 당황, 대기, 되묻기 같은 기능이 남아 있고 다음 내용을 상대가 가져오게 된다.

## 현재 프롬프트에서 확인한 구체적인 문제

### 예시 2는 기존 조사에 적힌 농담의 논리가 바뀌었다

기존 조사 문서는 ‘그 작품을 읽고도 안 슬프면 사람이 아니다’라는 농담 뒤에 상대가 안 읽었다고 하자 `사람인지아닌지`가 중첩 상태라고 이어간 것으로 기록한다. 현재 페르소나 예시 2는 앞의 전제를 없애고 `봤는지안봤는지`가 중첩 상태라고 바꿨다.

상대가 안 봤다고 이미 말했으므로, 현재 예시는 알려진 사실을 다시 모른다고 하는 셈이다. ‘문맥을 이해한 농담’이 ‘과학 단어를 붙인 농담’으로 바뀐 명확한 예시 결함이다. 이 판단은 기존 조사 문서와 현재 프롬프트의 대조에 근거하며, 9월 15일 원문을 이번에 다시 열어 검증한 것은 아니다.

### 예시 1은 서로 다른 턴을 합쳤다

기존 조사에는 `만들어라`와 `재밌겠네` 사이에 다른 참여자의 발언이 있었다고 명시되어 있다. 현재 예시에서는 하나의 입력에 두 메시지를 모두 출력한다. 짧게 받고 끝날 장면에서도 모델이 다음 반응까지 먼저 말하게 만드는 예시다.

### 창작 예시가 일정한 완성도를 요구한다

예시 7~14는 창작 예시라고 명시되어 있지만, 짧은 반응 뒤에 이유, 재치 있는 문장, 질문을 덧붙이는 구성이 반복된다. 예를 들어 `그게더무서운데` 뒤에는 이유가, `그건암호화임` 뒤에는 교훈이 붙는다. 규칙에 ‘매번 설명하지 말라’고 적혀 있어도 출력 예시는 추가 문장을 정상적인 끝맺음으로 보여준다.

특히 ‘생각이 있으면 이유를 구체적으로 붙인다’는 지시와 ‘한마디면 끝내도 된다’는 지시가 경쟁한다. 길이를 더 제한하기 전에 한마디만으로 기능을 마친 응답을 충분히 보여주는 편이 적절하다.

### 말투 평가와 도우미 성능 평가가 섞여 있다

현재 평가 문서는 코드를 제대로 제공하는지, 긴 기술 설명이 가능한지, 페르소나가 유지되는지에 집중한다. 이는 유용한 제품 기준이지만, 특정 화자와 닮았는지는 별도다. 반말로 정확하게 설명하고 농담을 넣어도 일반적인 친근한 AI일 수 있다.

## 현재 CLI에서 직접 확인한 출력

아래는 각각 새 프로세스에서 한 번씩 실행했다. `--no-update --no-session --print`를 사용했고 프롬프트를 수정하지 않았다. Discord 대화 전체를 모델 입력으로 넣지 않고 짧은 합성 입력을 사용했다. 실행 당시 기본 모델 설정을 사용했으며 모델·thinking을 별도로 고정하거나 확인하지 않았으므로, 모델 간 비교나 빈도 추정으로 해석하지 않는다.

| 입력 | 실제 출력 (`/`는 메시지 구분) | 관찰 |
| --- | --- | --- |
| 어이 전서구. | 어이 / 불렀으면 용건을 말하쇼 | 본인의 해당 장면 자기평가인 `?`보다 캐릭터 대사를 추가함 |
| 너를 주제로 CLI 만들어서 유명해질 거임 | 오 / 드디어 인간이 아니라 명령어로 소환되는 거임 / `jeonseogu --help` 치면 도움말 대신 “모름...” 뜨게 하자 | 기술 소재의 농담을 이어 붙이고, 문맥상 불확실성이 없는데도 `모름`을 개그로 가져옴 |
| 이 소설 읽고 안 울면 로봇이라며. 근데 나는 아직 안 읽었는데 | 그럼 아직 인간 판정 유예임 / 읽고 안 울면 그때부터 펌웨어 검사 들어감 | 전제는 이해했지만 추가 기술 농담까지 완성함 |

세 출력 모두 문법이나 뜻이 망가진 것은 아니다. 이번에 본 실제 화자와 비교할 때, 가벼운 입력에서도 정돈된 농담을 끝까지 만들어내는 경향이 문제 후보로 드러났다. 프롬프트 예시가 원인이라는 설명은 유력한 가설이며, 동일 모델·설정의 변경 전후 비교로 아직 검증하지 않았다.

## 다음 수정과 평가의 우선순위

1. **전제와 턴 경계부터 바로잡기.** 기존 예시 1·2를 원래 문맥에 맞추고, 중간 상대 발언을 삭제해 하나의 출력으로 합치지 않는다. 실제 관찰을 각색한 예시도 원문과 구분한다.
2. **반응 하나로 끝나는 예시 보강.** 부름, 짧은 정정, 웃음, 대화 종료에 설명과 질문이 없는 응답을 포함한다. `?`를 모든 상황의 고정 정답으로 만들지는 않는다.
3. **짧은 문장 여러 개와 한 문장의 분할을 구분.** 분할 횟수보다 각 메시지가 같은 발화를 잇는지 본다. 상대 반응이 필요한 다음 장면은 미리 생성하지 않는다.
4. **창작 농담의 비중 줄이기.** 아무 반응에도 기술 비유를 더하는 예시 대신, 구체적 관심·정정·상황 속 입장이 드러나는 대화를 사용한다.
5. **긴 글의 자연스러움도 유지.** 자발적인 감상, 설명, 장난스러운 목록을 별도 장면으로 평가한다. 길이나 Markdown 사용 자체를 실패로 판정하지 않는다.
6. **평가에서 재미와 닮음을 분리.** ‘재미있다’, ‘도움 된다’, ‘전서구 같다’를 따로 묻는다. 모델과 thinking을 고정하고, 예시에 넣지 않은 문맥으로 반복 비교한다.

우선 비교할 장면은 단순 부름, 사실 하나의 정정, 다른 사람이 중간에 끼어든 농담, 예전 주제로 돌아가기, 구체적인 작품 감상, 긴 설명 이후의 짧은 대화 종료다. 평균 길이 하나보다 **이미 기능을 마친 뒤 불필요한 문장을 얼마나 더 붙이는지**와 **상대가 반응할 차례를 남기는지**를 평가하는 편이 이번 관찰에 맞는다.

### 이번에 더 분명해진 기준

- **반응의 크기:** 부름과 짧은 정정은 그 기능을 마쳤을 때 끝난다. 추가 설명의 유무를 단순 글자 수로 결정하지 않는다.
- **관심과 판단:** 개발과 작품 감상에서는 구체적으로 길게 말할 수 있다. 무조건 짧게 말하는 설정과 구분한다.
- **관계와 상황:** 자신을 대상으로 한 장난, 도움이 된 팁, 아쉬운 하루는 다른 반응을 요구한다. 말끝 몇 개로 모든 상황을 통일하지 않는다.
- **대화의 차례:** 중간의 상대 발언과 시간이 흐른 뒤의 말을 보존한다. 단독 발언을 보기 좋은 완성형 예시로 편집하지 않는다.
- **관찰과 제품 설계:** 실제 발언, 문맥을 줄인 예시, 새로 만든 기술 예시를 구분한다. 실제 인물의 삶과 취향을 모델의 경험으로 주장하지 않는다.

## 반영한 변경

`personas/jeonseogu.md`를 위 기준으로 다시 작성했다. 단독 반응을 허용하는 원칙을 앞에 두고, 이유와 기술 비유를 덧붙이는 창작 예시를 줄였다. 서로 다른 턴을 복원했으며, 따뜻한 반응과 긴 감상·코드 설명의 여지도 남겼다. 의미가 없는 동일 응답을 고정하는 것이 아니라 상황이 바뀌어도 같은 화자의 반응 방식이 유지되는 것이 목표다.

실행 경로에서는 `--no-context-files`가 pi의 `APPEND_SYSTEM.md` 자동 탐색을 막지 않는 것을 설치된 pi 소스로 확인했다. 기본 페르소나 사용 시 명시적인 빈 `--append-system-prompt`를 주입해 이를 차단했다. 이 경로가 이번 사용자의 응답을 오염시켰다는 증거는 없으며, 환경에 따라 다른 지시가 추가되는 가능성을 제거한 수정이다. 사용자가 직접 지정한 프롬프트 옵션은 유지한다.

반복 실험의 설정·원문 출력·판정은 [페르소나 평가](persona-evaluation.md)에 기록한다.
